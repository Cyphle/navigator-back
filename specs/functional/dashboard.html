Context

The dashboard is a personalizable weekly glance at the home page: a grid of widgets a user arranges to see, at a glance and without clicking, what matters for the current week across the other domains (calendar, meals, magic lists, bank accounts). Each user composes their own layout; the family in context scopes the entities a widget can point at.

State of the code: the front is real but predates this design — the home page shows a fixed set of sections (3 stat cards, agenda, magic lists, meals, bank accounts) built from five per-domain summary calls, plus a dormant aggregated GET dashboard/:familyId endpoint returning a static fixture. The back is a stub (summary returns []). The front contract is the reference but evolves here; the realignments are listed in their own section.

The week is the current calendar week, Monday → Sunday, dates inclusive.

Ownership & personalization

A dashboard layout is personal — it belongs to a user and is never shared (decision D3). It is scoped per (user, family): the same user gets a distinct layout in each family they belong to, because pinned widgets point at that family's entities. The layout is not a shareable resource, so the cross-cutting sharing mechanism does not apply to it (pinned entities still obey their own sharing — a widget can only pin something the user may access).

When the user has no family, the home page short-circuits to the existing "no family" overlay; no dashboard renders.

Widgets

A widget is one card on the grid. Two families (decision D5):

  • Global widgets are singletons: at most one per layout, no entity to pick.
  • Pinnable widgets are instanceable: added several times, each pinned to one entity (a specific list, account or calendar).

A pinned widget whose entity disappears (deleted, or the user loses access) is kept but flagged unavailable and can be removed; the back does not auto-prune it (decision D10).

Grid & customization

The grid has 2 columns (collapsing to 1 on mobile). Each widget carries a width (colSpan 1 or 2) and a height (COMPACT | NORMAL | TALL). Widgets flow top-to-bottom by position; there is no free x/y placement (decision D2). Height caps how many items a widget shows before a "+N more" affordance.

A "Customize" mode lets the user add a widget from the catalog, drag to reorder, resize (width/height), and remove. A new user starts on a default layout (decision D6): Agenda of the week (2 col) + Meals of the week (2 col) + Pressing tasks (1 col) + All accounts (1 col).

Data model

Only the database model is treated as technical here. A layout is a flat list of widget rows owned by a user within a family.

pub struct DashboardWidget {
    pub id: i32,
    pub owner_username: String,
    pub family_id: i32,
    pub kind: WidgetKind,
    pub entity_id: Option<i32>,       // required for pinnable kinds; None for globals
    pub col_span: i16,               // 1 | 2
    pub height: WidgetHeight,        // COMPACT | NORMAL | TALL
    pub position: i16,               // order within the layout
    pub created_at: DateTime,
    pub updated_at: DateTime,
}

pub enum WidgetKind {
    AgendaWeek, MealsWeek, PressingTasks, AllAccounts, ShoppingList,  // global
    MagicList, BankAccount, Calendar,                                 // pinnable
}
pub enum WidgetHeight { Compact, Normal, Tall }

Table: dashboard_widgets. A global kind appears at most once per (owner_username, family_id); a pinnable kind is unique per (owner_username, family_id, kind, entity_id) (no duplicate pin). entity_id has no foreign key (it is polymorphic — a list, account or calendar depending on kind), so the widget survives the entity and is flagged unavailable at read time.

JSON convention: camelCase (familyId, entityId, colSpan, height, position, createdAt, updatedAt). Enums in SCREAMING_SNAKE. Mutations return the full widget layout (the ordered list).

API contract — endpoints

The dashboard endpoint serves and edits only the layout; widget content reuses each domain's existing summary endpoints — the front composes (decision D8). Under families/{familyId}/dashboard:

  • GET /widgets → the caller's layout for the family: ordered [{ id, kind, entityId?, colSpan, height, position }].
  • POST /widgets → add a widget (kind, entityId?, colSpan, height, position).
  • PATCH /widgets/{id} → move/resize (position, colSpan, height).
  • DELETE /widgets/{id} → remove.

Widget content comes from: calendar summary scoped to the current week (agenda / calendar widgets), magic-lists summary + list detail (pressing-tasks / list widgets), bank-accounts summary (all-accounts / account widgets), the meal selection of the week and its generated shopping list (meals / shopping-list widgets).

Errors & HTTP codes

Project common principle, standard web codes: 401 no session, 404 absent widget, 403 pinning a widget to an entity the user cannot access, 400 invalid input (colSpan ∉ {1,2}, entityId missing for a pinnable kind or present for a global kind), 409 a second instance of a global kind, or a duplicate pin.

Listed edge cases

  • Pinned entity deleted / unshared → widget kept, flagged unavailable at read time; user removes it; back does not auto-prune (D10).
  • Second instance of a global widget → rejected (409).
  • Empty week (no events / no meal) → the widget renders its own empty state; meal days with nothing are flagged.
  • Account widgets under a weekly frame → they stay monthly (current month); only their card is not week-scoped.
  • No family → home overlay, no dashboard; queries gated on a family id.
  • Concurrent reorder → last write wins on position.

Decisions journal (revisable)

  • D1 — Dashboard = personalizable weekly glance, current calendar week Mon→Sun (dates inclusive).
  • D2 — Grid of 2 columns; each widget has a width (colSpan 1|2) and a height (COMPACT/NORMAL/TALL); widgets flow top-to-bottom by position, no free x/y placement.
  • D3 — A layout is personal (never shared) and scoped per (user, family).
  • D4 — Catalog: globals (Agenda week, Meals week, Pressing tasks, All accounts, Shopping-list shortcut) + pinnables (Magic list, Bank account, Calendar).
  • D5 — Global widgets are singletons; pinnable widgets are multiple, each bound to one entity.
  • D6 — Default layout for a new user: Agenda + Meals + Pressing tasks + All accounts.
  • D7 — Pressing tasks = uncompleted TASK-list items with dueDate in the current week or overdue, all visible lists, sorted by dueDate.
  • D8 — The dashboard endpoint serves only the layout; widget content reuses each domain's existing summary endpoints.
  • D9 — Stat cards / counters removed.
  • D10 — A pinned widget whose entity disappears is kept and flagged unavailable; the back never auto-prunes it.
  • D11 — The dashboard agenda uses the current calendar week Mon→Sun (not the rolling j→j+7 window the calendar summary uses elsewhere).
