Context

In family and personal life, time-bound items come up: holidays, birthdays, reminders, recurring chores. These items may concern one person, several members, or the whole family.

The general need: record events and tasks to do, get a view over time (agenda), and later get reminders. Google Calendar is used elsewhere; external sync is out of scope here.

State of the code: the front is real (full CRUD on calendars and nested events, plus an agenda summary). The back is a stub: only GET /families/{familyId}/calendars/summary exists and returns []. The front contract is the reference; deltas decided here are listed in their own section.

Data model

Only the database model is treated as technical here. A calendar is user-owned; access beyond the owner is delegated entirely to the cross-cutting sharing mechanism. No type / family_id / visibility columns (decision C1).

pub struct Calendar {

    pub name: String,
    pub color: String,
    pub owner_username: String,        // owner: the only one who administers the calendar
    pub created_at: DateTime,

}
// Sharing / access rights are NOT carried by calendar:

pub enum RecurrenceType { None, Daily, Weekly, Monthly, Yearly }

JSON convention: the API exposes camelCase (calendarId, endDate, allDay, reminderMinutesBefore, createdAt, updatedAt). Enums serialize in SCREAMING_SNAKE (EVENT, TASK, NONE, DAILY, WEEKLY, MONTHLY, YEARLY). invites is exposed as an array of member usernames. Mutations return the full Calendar aggregate.

Event temporal model

Three valid shapes (decision C2):

ShapeallDaytime / durationendDateUse
TimedfalserequirednoneSingle-day, at a time (dentist 10:00, gym 18:00)
All-day, singletruenull (ignored)noneBirthday, public holiday
All-day, multitruenull (ignored)setHolidays over [date, endDate]

Rules: a timed event is mono-day (no endDate). endDate implies allDay = true and must satisfy endDate ≥ date. When allDay = true, time/duration are null and ignored.

Events and tasks

An item is either an event (a moment in time) or a task (something to do by a date), distinguished by kind (decision C5). This intentionally overlaps a little with magic_list.

  • done is meaningful only when kind == TASK (default false); checking a task off does not delete it.
  • A task carries a due date (date); time is optional and it may be allDay; a task may recur (recurring chore).
  • For an EVENT, done stays false and is not surfaced.

Recurrence

Recurrence is a simple infinite rule (decision C3): NONE | DAILY | WEEKLY | MONTHLY | YEARLY. No end date, no per-occurrence exception. A recurring item is stored as one row plus its rule; occurrences are expanded by the back within the agenda window. Editing or deleting the item affects the whole series (no "this occurrence only"). Covers birthdays (YEARLY), recurring chores, weekly gym.

Invitees / participants

An invitee is a family member, identified by username (decision C4). Inviting is a label of who is concerned and a routing rule for the agenda:

  • Being invited makes the event appear in the invitee's agenda, even without any share on the owning calendar.
  • Invitation does not grant calendar access: opening the full owning calendar still requires a share.
  • "Invite the whole family" is a frontend convenience (expanded to one username per member), mirroring the sharing model.

Managing a calendar

Creation

A user creates a calendar with a name and a color. On creation it is personal (no sharing). A user may own several calendars.

Modification

  • Rename / recolor the calendar (owner only).
  • Manage sharing (add/remove/change grants): owner-only, through the cross-cutting sharing endpoint, not through calendar editing (see sharing.html).

Deletion

  • Deleting a calendar deletes its events (cascade) and its sharing grants (cross-cutting registry — see sharing.html).

Events (CRUD)

  • Add an event/task to a calendar.
  • Edit an event/task (any field, including invites and done).
  • Delete an event/task (deletes its invite rows in cascade).

Every event mutation returns the full Calendar aggregate (project convention).

Access & sharing

Access is delegated to the cross-cutting mechanism (sharing.html): the owner has full rights; other users see/edit a calendar only through a matching share grant (Linux-style bitmask). There is no calendar-specific access table.

  • A calendar with no matching share is invisible (404 on access).
  • A visible calendar without write rights → 403 on mutation.
  • Being an event invitee is independent of calendar access (see Invitees).

Agenda view (summary)

The core need — "a view of these items over time" — is served by the agenda summary (decision C7):

  • Endpoint GET /families/{familyId}/calendars/summary?from=&to=.
  • Aggregates, flattened, the events of all calendars the user can see (owned + shared) plus events where the user is an invitee (even without calendar access).
  • Recurring items are expanded into occurrences falling within [from, to].
  • Default window: if from/to are omitted, the back uses today → today + 7 days (one week).
  • Returns DashboardAgendaItem[] (id, title, time, person, calendarColor, attendees). The former visibility field is removed (no source since PERSONAL/SHARED was dropped, C1).

Reminders

reminderMinutesBefore is stored and exposed only (decision C6); no back-side triggering. Active notifications (scheduler + channel) are a dedicated cross-cutting brainstorm later.

Errors & HTTP codes

Project common principle, standard web codes: 404 absent/invisible calendar or event, 403 visible without the required right, 400 invalid input (temporal rules above, bad date/time format). Nothing domain-specific.

Listed edge cases

  • endDate < date → 400.
  • Timed event with endDate, or allDay with time/duration → reject/normalize per the temporal table → 400 on conflict.
  • done on an EVENT → ignored (stays false).
  • Invitee who is not a family member → out of scope; invites are members only.
  • Invitee with no share → event shows in their agenda but the calendar itself stays 404 to them.
  • Recurring multi-day all-day event → allowed; each occurrence spans [date, endDate] shifted by the rule.
  • Summary without from/to → back applies the default window today → today + 7 days (C7).

Open points

None.

Decisions journal (revisable)

  • C1 — Calendar is user-owned; sharing via the cross-cutting mechanism. No type/familyId/visibility on the calendar. The families/{id} path is a front grouping.
  • C2 — Add allDay + endDate?; time/duration only for timed mono-day events.
  • C3 — Recurrence is a simple infinite rule, no end, no per-occurrence exception; editing affects the whole series; back expands occurrences in the agenda window.
  • C4 — Invitee = member (username); being invited surfaces the event in their agenda without granting calendar access; "invite the family" is a front expansion.
  • C5 — Event kind EVENT/TASK + done (meaningful for TASK only).
  • C6 — reminderMinutesBefore stored/exposed only, no triggering.
  • C7 — Agenda summary aggregates all accessible calendars + invited events over a parametrable [from, to] window (default today → today+7), recurrences expanded. The agenda item's visibility field is removed (no source after C1).
