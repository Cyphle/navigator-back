Sharing (cross-cutting concept)

Date
2026-06-24
Status
brainstorm complete — see decisions journal (T1→T9) at the end

This is not a functional theme but a central mechanism: every shareable domain (magic_list, calendar, accounts, recipes, meals, …) relies on it. Goal: one single sharing mechanism, a common user journey, and unified monitoring.

Base principle

By default, nothing is shared: every element is personal (belongs to its creator). It can then be shared with other users.

Sharing is done per user. The back only reasons in individual grants (resource → user → right). It does not know the notion of "share with a family": that is a frontend convenience (see below).

The 3 key notions

1. Visibility (derived)

  • PERSONAL: no grant → only the owner has access.
  • SHARED: at least one grant exists.

Visibility is not a column: it is derived from the existence of grants.

2. Ownership (owner)

Every element has an owner (its creator). The owner is above the rights: only they can administer the element — rename it, manage its sharing (add/remove grants) and delete it. Administration is never delegated (even a user with write cannot administer).

3. Access rights — Linux-style bitmask

Rights apply to the content of the element (the items of a list, the events of a calendar, etc.). We reuse the Linux permission encoding:

BitRightValue
rread4
wwrite2
x(reserved, unused)1

Write implies read. In iteration 1, a grant carries one of these 2 values:

ValueMeaningNotation
4read-onlyr--
6read + writerw-

No grant = no access (equivalent to 0 / ---). Testing rights: access & 4 ⇒ can read · access & 2 ⇒ can write.

Sharing an element

The owner shares an element by creating grants: for each userId, a right (4 or 6).

  • Add a grant = give access to a user.
  • Change a grant = change its right (4 ⇄ 6).
  • Remove a grant = cut access (the element becomes personal again if none remain).

How access is resolved

Effective access of a user U on a resource R:

  1. if U == owner(R) → full access (rw) + administration;
  2. otherwise, if a grant exists for (R, U) → the right of that grant (4 or 6);
  3. otherwise → no access.

No family-membership check: the individual grant is the source of truth. Administration (rename / sharing / deletion) stays owner-only, independent of the bitmask.

"Share with the family" = frontend convenience

On the back side, no notion of family in sharing. On the front side:

  • "Share with my family" = the front iterates the members of the family and creates one grant per user (chosen right, e.g. 6). Excluding someone = not creating their grant.
  • The display may group grants by family ("shared with the Dupont family"); this is purely presentation.

Accepted consequences:

  • Snapshot, not dynamic: a member who joins the family after the share does not get automatic access. The front can re-offer a "re-share with the family".
  • Leaving the family does not remove access: with no membership check, a grant stays valid until the owner revokes it. (The front can offer a cleanup action.)

This choice radically simplifies the back: no family_id, no default level, no overrides, no sharing → family dependency.

Data model

A central, generic (polymorphic) registry, in common/, one single table:

CREATE TABLE shares (
    id             SERIAL PRIMARY KEY,
    resource_type  VARCHAR(40) NOT NULL,   -- 'MAGIC_LIST', 'CALENDAR_EVENT', 'BANK_ACCOUNT', ...
    resource_id    INTEGER     NOT NULL,   -- id of the element in its business table (NO FK: polymorphic)
    user_id        INTEGER     NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- grant beneficiary
    access         SMALLINT    NOT NULL,   -- bitmask {4, 6}
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (resource_type, resource_id, user_id)   -- at most 1 grant per (resource, user)
);

Consequences:

  • A grant exists only if the element is shared with that user. Personal = no row.
  • The business element keeps its owner_id; the registry stores only the grants (neither ownership nor content).
  • resource_id has no FK (polymorphic registry) ⇒ deleting a business element must delete its grants explicitly (no DB cascade possible on a polymorphic key).
  • user_id references users.id (global id).

The software architecture (where this module lives, layering, traits, injection) is not covered here: it follows the project's clean/hexagonal architecture rules.

Errors & HTTP codes

Sharing follows the common error principle of the whole project (see CLAUDE.md), reinventing nothing: each layer can raise an error, wrapped and re-mapped at each traversed layer (hexagonal), up to the controller, preserving the cause chain via #[source].

  • a SQL error → RepositoryError (NotFound / Conflict / Technical(#[source] …));
  • wrapped by the use-case error (variants carrying context: resource_id, user_id);
  • converted to MiddlewareError (#[from]) then to an HTTP response.

HTTP codes per standard web codes:

SituationCode
Not authenticated401
Read access denied (neither owner nor grant)404 (we do not reveal existence)
Action denied while having read (write without w, or admin by non-owner)403
Conflict (e.g. grant already present)409
Technical error500 (body neutralized, chain logged)

API

The registry is a server implementation detail; the API stays resource-oriented (aligns the front, reference contract):

  • each resource returns its shares: sharedWith = [{ userId, access }], the caller's effective access, and a derived visibility PERSONAL/SHARED (computed back-side: SHARED ⇔ sharedWith non-empty) to match the visibility badge already shown by the front;
  • the mutation of shares goes through a resource endpoint (e.g. PUT /magic-lists/{id}/shares with the desired list of grants), executed by the owner;
  • "share with the family" is expressed front-side as a sharedWith populated with the members' userId; the back only sees individual grants;
  • no cross-cutting monitoring endpoint in iteration 1 (the central registry will make it trivial later — out of scope).

Convention: JSON camelCase, access values as integers (4 / 6).

Concrete example — magic_list

magic_list is the first consumer and serves as a migration example.

Before (model specific to magic_list): columns visibility, family_id, excluded_user_ids INTEGER[] on the magic_list table, and a homemade check_magic_list_access based on family membership.

After (cross-cutting per-user model):

  • we remove visibility, family_id, excluded_user_ids from magic_list (we keep owner_id);
  • sharing a list = rows shares(resource_type='MAGIC_LIST', resource_id=<listId>, user_id, access);
  • check_magic_list_access delegates to resolve_access(ResourceType::MagicList, listId, user, owner_id);
  • rights: any user with w can add/check/edit/delete items and clear the completed ones; only the owner renames / manages sharing / deletes the list.

Migration of existing data:

  • for each SHARED list: create a grant access = 6 (the old sharing was collaborative) for each member of the target family except those present in excluded_user_ids;
  • then drop the columns visibility, family_id, excluded_user_ids.

The "Access & sharing" section of magic-list.html has been amended to follow this model (per user, bitmask, owner-only admin).

Edge cases

  1. Member joins the family afterwards: no automatic access (snapshot). Front possibly offers a "re-share".
  2. Member leaves the family: their grant stays valid until the owner revokes it (no membership check). Front may offer a cleanup.
  3. Deleting a user: ON DELETE CASCADE on shares.user_id removes their grants.
  4. SHARED → PERSONAL switch: = remove all grants.
  5. Bitmask values outside {4,6}: rejected on write (validation) in iteration 1.
  6. Grant on oneself / on the owner: ignored / forbidden (the owner already has full access).

Decisions journal (revisable)

  • T1 — Granularity: sharing per element (generalization of magic_list), no "spaces".
  • T2 — Rights = Linux bitmask: r=4, w=2, x=1 (reserved). w implies r ⇒ a grant is 4 or 6; no grant = no access.
  • T3 — Owner-only administration: rename / sharing / deletion reserved to the owner; write only applies to content.
  • T4 — Beneficiary key = global user_id (exposed as userId).
  • T5 — Central generic registry in common/, one single shares table of grants (resource_type, resource_id, user_id, access), row only if shared; the element keeps owner_id.
  • T6 — Access resolution: owner → full + admin; otherwise grant (R, user); otherwise no access. No family-membership check.
  • T7 — API embedded per resource (sharedWith + effective access + derived visibility PERSONAL/SHARED), internal registry; no monitoring endpoint in iteration 1.
  • T8 — Sharing is PER USER. "Share with a family" = frontend convenience (expansion into N individual grants) + display grouping. The back does not know families in sharing. Accepted consequences: snapshot (no dynamic inheritance); leaving the family does not remove access.
  • T9 — Errors & HTTP: follows the project principle (wrapping + re-mapping at each layer, #[source] chain, propagation to the controller). Standard web codes: 401 / 404 (read denied, not revealed) / 403 (write without w or admin by non-owner) / 409 / 500.
