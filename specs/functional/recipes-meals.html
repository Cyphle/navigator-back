#5 recipes & planned meals (front real / back stub)

Context

Two linked domains. Recipes is a personal/shared cookbook. Meal selection lets the user pick recipes and place them on days to plan what to cook over the coming days, then turn that into a shopping list.

The brainstorm was driven by the real usage: "I pick recipes for the next week or two, I say this dish is for Monday and Tuesday, and from the selected recipes I build a shopping list." State of the code: the front is real (recipe browsing, rating, meals lists CRUD, summaries); the back is a stub. The front contract is the reference; deltas decided here are listed in their own section.

Ownership & sharing

A recipe and a meal selection are user-owned (decision R1). The front visibility/familyId notions are removed; access beyond the owner is delegated to the cross-cutting sharing mechanism (see sharing.html). Invisible → 404, visible without write right → 403. The families/{familyId} path segment is a front grouping.

Recipes — the cookbook

A recipe captures what to cook and how. The user creates, edits, deletes recipes (full CRUD, decision R5) and browses the catalogue with search, category filter, minimum rating and sort (paginated, from the front contract).

  • Identity: name, category (ENTREE / PLAT / DESSERT / SAUCE / APERO), a presentation image.
  • Ingredients: a structured list — each is { quantity?, unit?, name } (decision R3). The structure is what makes the shopping list summable. Free wording stays possible by leaving quantity/unit empty (e.g. "a bit of salt").
  • Steps: an ordered list of preparation steps; each step can carry an image (decision R2). No "parts" split — a recipe is flat (ingredients + steps).
  • Rating: a single shared value per recipe (decision R6); anyone with access sees and changes it.
  • Favorite: per member (decision R6) — my own shortlist, independent of others'.
  • Images: uploaded through the back; the physical storage backend is abstracted (decision R4) and out of functional scope. A recipe/step holds an opaque image reference.

Meal selection — planning

From the cookbook the user clicks "start a selection" and builds a working set of recipes, positioning each on days (decision R7).

  • A selection is a set of placements (recipe → day). A recipe may be placed on several days ("this dish is for Monday and Tuesday").
  • No frozen period: a selection has no fixed start/end. The user keeps positioning recipes freely. Any displayed range is derived from the earliest/latest placed day.
  • No lunch/dinner slot, no per-person targeting — a meal is a family meal, reasoned by day.
  • Full CRUD on a selection; user-owned and shareable.

Shopping list — bridge to Magic List

From a selection the user clicks "validate" and the app creates a checkable Magic List (decision R8, see magic-list.html).

  • Aggregation: same ingredient + same unit → summed into one line (200 g + 200 g = 400 g flour).
  • Unit conflict: same ingredient, different units → one line flagged "to check", the heterogeneous quantities listed in its comment ("200 g + 3 spoons + 2 ladles"). The user fixes the quantity manually and confirms to clear the flag.
  • Source link: the generated list remembers the recipes that fed it. Removing a recipe triggers a best-effort subtraction of its quantities: compatible unit → subtracted; incompatible unit → left untouched. No guarantee — pragmatic by design.
  • Free adjustment: the user adds, edits and deletes items at will (it is a normal Magic List).

Dashboard

The dashboard shows the calendar and, alongside, the recipes positioned on the currently visible days. There is no "selected this week" marker (decision R9) — what shows is simply the placements falling in the visible window. The exact window is a dashboard concern (theme #6), consistent with the calendar agenda.

Data model

Only the database model is treated as technical here.

pub struct Recipe {
    pub id: i32,
    pub owner_username: String,
    pub name: String,
    pub category: RecipeCategory,
    pub image_ref: Option<String>,     // opaque reference; storage abstracted (R4)
    pub rating: Option<i32>,            // single shared value (R6)
    pub ingredients: Vec<RecipeIngredient>,
    pub steps: Vec<RecipeStep>,
    pub created_at: DateTime,
    pub updated_at: DateTime,
}

pub struct RecipeIngredient {          // structured (R3)
    pub id: i32,
    pub recipe_id: i32,
    pub quantity: Option<BigDecimal>,
    pub unit: Option<String>,
    pub name: String,
    pub position: i32,
}

pub struct RecipeStep {
    pub id: i32,
    pub recipe_id: i32,
    pub position: i32,
    pub text: String,
    pub image_ref: Option<String>,     // per-step image (R2)
}

pub enum RecipeCategory { Entree, Plat, Dessert, Sauce, Apero }

// recipe_favorites { recipe_id, username }   // favorite per member (R6)

pub struct MealSelection {             // no frozen period (R7)
    pub id: i32,
    pub owner_username: String,
    pub name: Option<String>,
    pub created_at: DateTime,
    pub updated_at: DateTime,
    pub entries: Vec<MealSelectionEntry>,
}

pub struct MealSelectionEntry {        // one row per covered day
    pub id: i32,
    pub meal_selection_id: i32,
    pub recipe_id: i32,

}

Tables: recipes, recipe_ingredients, recipe_steps, recipe_favorites, meal_selections, meal_selection_entries, shopping_list_links. The shopping list itself is a regular Magic List (its own domain). Sharing reuses the cross-cutting shares table — no family/visibility column.

JSON convention: camelCase (imageUrl, ownerUsername, createdAt, updatedAt); enums in SCREAMING_SNAKE (ENTREE, PLAT, …). Mutations return the full aggregate (recipe, or meal selection).

Errors & HTTP codes

Project common principle, standard web codes: 404 absent/invisible recipe or selection, 403 visible without the required right, 400 invalid input (empty name, bad category, malformed ingredient/step, day not a valid date).

Listed edge cases

  • Ingredient with no quantity/unit ("a bit of salt") → allowed; never summed, listed as-is.
  • Same ingredient, same unit, across recipes → summed into one shopping line (R8).
  • Same ingredient, different units → one flagged line with the detail in its comment; user fixes and clears the flag (R8).
  • Removing a recipe from a generated list, incompatible unit → quantity left untouched, best-effort (R8).
  • Recipe placed on several days → one entry per day; counts once per day in the meal display.
  • Deleting a recipe still referenced by a selection → to define at implementation (keep the placement name vs cascade); functionally the placement should not crash the selection view.

Open points

Decisions journal (revisable)

  • R1 — Recipe and meal selection are user-owned; sharing is cross-cutting.
  • R2 — Recipe is flat (ingredients + steps), no parts[]; each step can carry an image; recipe has a presentation image.
  • R3 — Ingredients are structured { quantity?, unit?, name } (enables shopping-list summation).
  • R4 — Images are uploaded through the back; storage backend is abstracted (opaque reference); out of functional scope.
  • R5 — Full CRUD on recipes.
  • R6 — Rating is a single shared value per recipe; favorite is per member.
  • R7 — Meal selection started from the cookbook; placements (recipe → day), a recipe may cover several days; no frozen period; no slot, no per-person.
  • R8 — "Validate" generates a checkable Magic List: same-unit ingredients summed; different units flagged "to check" with detail; list keeps a link to source recipes; removing a recipe subtracts best-effort (compatible unit only); free add/edit/delete.
  • R9 — No selectedForWeek marker; the dashboard shows recipes positioned on the visible days.
