Configuration — families & profile

Date
2026-06-24 (rev. 2026-07-17)
Status
brainstorm complete — see decisions journal (CF1→CF11) at the end

Two sub-domains under one theme: family governance (who is in a family, who can do what, how a family is born and dies) and the user profile (self-service, minimal). Authentication is delegated to Keycloak; all authorization lives in Navigator.

Scope & boundary

  • Keycloak = authentication only: it proves who you are at login (email / username / password, OIDC tokens). It knows nothing about families or rights.
  • Navigator = authorization + profile: family membership, the admin role, invitations and reactivation are all modelled in the Navigator database. Keycloak roles are not used for authorization.

Roles & governance

Creator — audit only

Every family records its creator (created_by): an immutable audit attribute. The creator has no permanent power. If they lose the admin role they become an ordinary member (or a non-member); they remain only historised as the creator. There is no permanent owner of a family.

Reconciliation with the sharing model. In sharing.html, every shared element has a single permanent owner (its creator) who alone administers it. A family follows the opposite rule: no permanent owner, governance by a collective admin role; the creator is pure audit. The two models are intentionally different — an element is owned, a family is governed.

Admin role — source of all powers

All family powers derive from the admin role:

  • invite / remove members,
  • grant / revoke the admin role,
  • rename the family / change its photo,
  • archive the family and reactivate it.

The creator is admin at creation. An admin can grant the admin role to any member ⇒ several admins are possible.

Revocation — "all revocable"

Any admin can revoke the admin role of anyone, including the creator. The only guard is an invariant: at least 1 admin as long as the family has members. Any operation that would leave a member-bearing family with zero admins is blocked.

Members

  • Invite & remove: admins only. A plain member cannot invite or exclude anyone.
  • Leave: everyone. Any member can leave the family on their own.
  • Last admin cannot leave (nor be demoted / removed) without first promoting another member. Same invariant guards removal and demotion — you never remove the last admin.
  • If the last admin is also the last member, leaving archives the family (see End of life).

Invitations

An admin invites an existing Navigator user — identified by email or username (two ways to designate the same account). There is no external onboarding (no invite of a non-registered person) and no shareable link / code.

Flow: admin invites → an in-app invitation is created (state pending) → the invitee accepts (becomes a member) or declines.

Lifecycle rules:

  • Decline → the invitation disappears; the admin may re-invite later.
  • Cancel → an admin can cancel a still-pending invitation.
  • No duplicate → at most one pending invitation per (family, user).
  • No expiry → a pending invitation stays valid until someone acts on it.

Membership & creation

  • A user can belong to several families at once (e.g. their own family and their spouse's family).
  • A user can create as many families as they want; on creation they become creator + first admin.
  • Every family operation is scoped by familyId (the user switches between their families).

End of life — soft delete with grace period

  1. A family becomes archived (soft delete): hidden, read-only, data kept. Triggers: an admin archives it explicitly, or the last member leaves.
  2. During the grace window, any admin can reactivate it → back to active.
  3. After X days without reactivation → hard delete: permanent purge.

A family archived by abandonment has 0 admins, so nobody can reactivate it → it always ends in hard delete. Only a family archived while it still has admins is reactivable.

Open point — scope of the hard-delete purge. The design says the purge removes the family's data (magic lists, bank accounts, calendar, recipes/meals). But per sharing.html those resources are user-owned (personal, shared per user) — the back does not attach them to a family. So "the family's data" is ambiguous: it must be decided whether domain resources are family-scoped or user-scoped before the purge cascade can be specified. Until reconciled, the hard delete removes only the family itself and its membership / invitations; the fate of domain resources is TBD. The grace duration X is a constant to fix later (e.g. 30 days).

Profile

Each user owns a Navigator profile, populated at first login from their Keycloak identity but independent afterwards. Minimal by design:

  • Editable (self-service): display name (how the user appears to others — in lists, agenda, invitations…) and an optional photo / avatar.
  • Read-only (from Keycloak): email and username, shown for identification, not editable in Navigator. Password is managed entirely by Keycloak.
  • No preferences (language, theme…) for now.

Data model

Families — the family aggregate. Active ⇔ archived_at IS NULL.

CREATE TABLE families (
    id           SERIAL PRIMARY KEY,
    name         VARCHAR(120) NOT NULL,
    photo_url    TEXT,                         -- optional
    created_by   INTEGER     NOT NULL REFERENCES users(id),  -- immutable audit, no power
    archived_at  TIMESTAMPTZ,                  -- NULL = active; set = soft-deleted (grace running)
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

Membership — one row per (family, user). The admin role is a boolean; exposed as role = ADMIN / MEMBER.

CREATE TABLE family_members (
    family_id  INTEGER     NOT NULL REFERENCES families(id) ON DELETE CASCADE,
    user_id    INTEGER     NOT NULL REFERENCES users(id)    ON DELETE CASCADE,
    is_admin   BOOLEAN     NOT NULL DEFAULT FALSE,
    joined_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (family_id, user_id)
);

Invitations — only pending rows exist (accept ⇒ membership row + delete; decline / cancel ⇒ delete). The unique key enforces "no duplicate".

CREATE TABLE family_invitations (
    id          SERIAL PRIMARY KEY,
    family_id   INTEGER     NOT NULL REFERENCES families(id) ON DELETE CASCADE,
    user_id     INTEGER     NOT NULL REFERENCES users(id)    ON DELETE CASCADE,  -- invitee, must exist
    invited_by  INTEGER     NOT NULL REFERENCES users(id),                       -- the admin
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (family_id, user_id)                 -- at most 1 pending invite per (family, user)
);

Profile — added on the existing users table. email / username come from Keycloak (read-only in Navigator).

ALTER TABLE users
    ADD COLUMN display_name VARCHAR(120),       -- editable
    ADD COLUMN avatar_url   TEXT;               -- editable, optional
-- email, username: synced from Keycloak, read-only

Notes:

  • The ≥ 1 admin invariant, last-admin-cannot-leave and promote-before-leaving are enforced in the use case (not by a DB constraint).
  • Hard delete is a scheduled purge running X days after archived_at; scoped to families + its family_members / family_invitations (cascade). Domain-resource purge is TBD (see open point above).

Errors & HTTP codes

Follows the project error principle (see CLAUDE.md): each layer wraps & re-maps, cause chain preserved via #[source]. Standard web codes:

SituationCode
Not authenticated401
Action reserved to admins (invite / remove / promote / rename / archive by a non-admin)403
Family not found, or caller not a member (existence not revealed); invitee email/username matches no existing user404
User already a member; duplicate pending invitation; would leave the family with 0 admins (last admin leave / remove / demote)409
Invalid payload (neither email nor username given; empty name)400
Technical error500 (body neutralized, chain logged)

Edge cases

  1. Last admin leaves / demoted / removed: blocked (409) — must promote another member first.
  2. Last member leaves: family archived; 0 admins ⇒ not reactivable ⇒ hard delete after X days.
  3. Invite a user already a member: 409.
  4. Duplicate pending invitation: 409 (unique key).
  5. Invite an email/username with no Navigator account: 404 (no external onboarding).
  6. Creator loses admin: keeps only the created_by audit trace; no reactivation power (reactivation belongs to any admin, not to the creator specifically).
  7. Reactivate past the grace window / an already-active family: 404 / 409.
  8. Deleting a user account: memberships & invitations cascade; the effect on a family whose last admin was that user is TBD (tie-in with the account-deletion flow, out of scope here).

Decisions journal (revisable)

  • CF1 — Two sub-domains: family governance + minimal profile, under one "configuration" theme.
  • CF2 — Creator = audit only: immutable created_by, no permanent power; no permanent family owner.
  • CF3 — Admin role = source of all powers; the creator is admin at creation.
  • CF4 — Grant admin: any admin can promote a member ⇒ several admins possible.
  • CF5 — "All revocable": any admin can revoke anyone's admin (creator included); invariant ≥ 1 admin while the family has members.
  • CF6 — Members: invite & remove = admins only; leave = everyone; last admin must promote before leaving (same invariant guards remove / demote).
  • CF7 — Invitations: by email/username of an existing user; in-app accept/decline; decline & cancel remove it; no duplicate; no expiry. No external onboarding, no link/code.
  • CF8 — Membership & creation: multi-family membership; unlimited family creation (creator = first admin).
  • CF9 — End of life: soft delete (archive) → reactivation by any admin within X days → else hard delete. Abandoned families (0 admins) are never reactivable.
  • CF10 — Profile: minimal — editable display name + avatar; email/username read-only (Keycloak); no preferences.
  • CF11 — AuthN/AuthZ boundary: Keycloak authenticates only; all authorization (families, roles, invitations) lives in the Navigator database.

Open points to reconcile

  • Hard-delete scope: depends on whether domain resources are family-scoped or user-scoped — currently user-scoped per sharing.html. Until decided, hard delete purges only the family + membership + invitations.
  • Grace duration X: constant to fix (e.g. 30 days).
  • Account deletion: interaction with the ≥ 1 admin invariant when the deleted user was a family's last admin — to be defined with the account-lifecycle flow.
