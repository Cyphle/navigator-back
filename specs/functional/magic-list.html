Context

We use lists every day: shopping lists, holiday packing lists, task lists, toy lists, and so on.

We use them in different contexts: planning the week's meals, preparing for holidays, the work to finish, etc.

We use them on different timeframes: for today, for tomorrow's shopping, for the holidays in two weeks, etc.

Sometimes we need lists we reuse several times, such as the list of things to take on holiday.

Navigator's Magic Lists answer all these needs simply: lists that are replicable, shareable, checkable. They must be easy to reach and intuitive.

Data model

pub struct MagicList {
    pub id: i32,
    pub name: String,
    pub list_type: MagicListType,
    pub owner_username: String,        // owner: the only one who administers the list
    pub created_at: DateTime,
    pub updated_at: DateTime,
}

// Visibility, sharing and access rights are NOT carried by magic_list:
// they belong to the cross-cutting mechanism (see sharing.html).
// The magic_list table therefore only keeps owner_id; no family_id /
// visibility / excluded_user_ids columns.

pub enum MagicListType { Simple, Task, Template }

pub struct MagicListItem {
    pub id: i32,
    pub magic_list_id: i32,
    pub title: String,
    pub content: Option<String>,        // OPTIONAL (see decision D2)
    pub checked: bool,
    pub due_date: Option<NaiveDate>,
    pub status: Option<MagicListItemStatus>,
    pub created_at: DateTime,
    pub updated_at: DateTime,
}

pub enum MagicListItemStatus { Todo, InProgress, Done }

JSON convention: the API exposes camelCase (magicListType, dueDate, itemCount, createdAt, updatedAt) to align with the front contract. Enums are serialized in SCREAMING_SNAKE (SIMPLE, TASK, TEMPLATE, TODO, IN_PROGRESS, DONE).

The sharing fields (derived visibility PERSONAL/SHARED, sharedWith = [{ userId, access }], the caller's effective access) are added to the view by the cross-cutting sharing layer (see sharing.html), not by magic_list itself.

List types and the completion model

Two "done" mechanisms coexist — checked (boolean, shopping-list model) and status (TODO / IN_PROGRESS / DONE, task-board model). The list type decides which UI is presented:

TypeUsagecheckedstatusDetail UI
SIMPLENotes / single-use reference listunusedunusedflat items, no checkbox
TASKActionable list (checkable shopping items and/or status todos)yes (checkbox)optionalcheckbox + status menu, grouping by status
TEMPLATEReplicable model (see Templates section)n/a (model)n/amodel editing

Decision D1: we keep 3 types. checked and status may coexist on a TASK list. The checkbox is shown only for TASK; the status menu is offered on TASK items.

Managing a Magic List

Creation

As a user, I create a magic list by specifying:

  • a name;
  • a type (SIMPLE / TASK / TEMPLATE).

On creation the list is personal (no sharing). Sharing is a distinct action handled by the cross-cutting mechanism (see sharing.html): the owner grants access per user; "share with the family" is a frontend convenience (one grant per member).

Modification

  • Rename the list (owner only).
  • Manage sharing (add/remove/change grants): an owner-only action that goes through the cross-cutting sharing endpoint, not through list editing.

Deletion

  • Deleting a list deletes its items (cascade) and its sharing grants (explicit deletion, polymorphic registry — see sharing.html).
  • Deleting a TEMPLATE does NOT delete the lists generated from it (no hard link / FK cascade; see Templates).

List items

An item has a mandatory title and an optional content (decision D2). Additional optional fields: dueDate, status, checked (for TASK).

Features:

  • Add an item.
  • Edit an item (title, content, dueDate, status, checked).
  • Delete an item.
  • Clear "completed" items: bulk-delete the items considered completed.

Unified "completed" rule: an item is completed if checked == true or status == DONE. (Aligns the "Clear" button and the "Completed" grouping of the front, currently inconsistent: the mock filters on status === DONE alone.)

Templates (flagship feature — Phase 2)

A template is a TEMPLATE-type list serving as a reusable model.

  • From a template, generate an instance of type SIMPLE or TASK, with its own name and its own visibility.
  • Generation copies the template's items; on the instance, checked is reset to false and status is reset (or removed).
  • The instance is independent: no persistent link to the template. Editing/deleting the template does not affect already-generated instances.

Access & sharing

The access/sharing mechanism is cross-cutting (see sharing.html) — sharing per user, bitmask rights (4 read / 6 write), resolution owner → grant → nothing. This section only describes its application to magic_list.

  • the owner always has full access to their lists and is the only one to administer them;
  • a non-owner accesses a list only if they have a grant on it; their right (4 or 6) is resolved by the cross-cutting layer;
  • write (6) on a list = collaborate on the ITEMS: add / check / edit / delete items, clear completed;
  • read-only (4) = view the list and its items, no modification;
  • owner only: rename, manage sharing, delete the list, regenerate from a template.

Visualization

Lists home page (summary)

  • Card view: name, visibility badge, type (icon + label), item count.
  • Filters: by type, by visibility, search by name.
  • Inline delete action (owner).

Filters/search on the front side at first (low volume). Backend query params may be added later if needed.

List detail page

  • Items adapted to the type (see list types table).
  • For TASK: grouping by status by default — "To do" / "In progress" / "Done".
  • Sorting possible by name / status / checked.
  • dueDate shown (DD/MM/YYYY), highlighted as overdue if past due and item not completed.

Listed edge cases

  1. Personal & multi-family lists: a list with no grant is global to the owner, visible whatever the active family context (sharing is per user, not bound to a family — see sharing.html).
  2. SHARED → PERSONAL transition: = remove all grants; the list disappears from other users' views.
  3. Owner / member leaves the family: without a membership check, existing grants remain valid until the owner revokes them (see cross-cutting edge cases).
  4. Member without a grant: does not see the list in the summary; 404 on direct access (we do not reveal existence).
  5. Manual reordering: no position column today → drag & drop not supported in phase 1 (sort by name/status/checked only). To add (a position column) if needed later.
  6. dueDate & timezone: "overdue" comparison against the local date of the day.
  7. Template deletion: does not break instances (no FK).

Implementation strategy

Contract reference: React front + Fastify mock (camelCase, response = full list after every item mutation, createdAt/updatedAt everywhere). The Rust back aligns to it.

Phase 1 — CRUD & access parity (Rust back ↔ front)

The back must catch up to the routes the front already expects. Endpoints to add:

MethodRouteTo do
GET/families/{familyId}/magic-lists/{id}new: detail + items (+ sharing block from the cross-cutting layer)
PUT/families/{familyId}/magic-lists/{id}new: rename (owner) — no visibility/exclusions here anymore
PUT/families/{familyId}/magic-lists/{id}/sharesnew: manage grants (owner-only) — delegates to cross-cutting sharing
DELETE/families/{familyId}/magic-lists/{id}new (deletes items + grants)
DELETE/families/{familyId}/magic-lists/{id}/items/{itemId}new (response = full list)
DELETE/families/{familyId}/magic-lists/{id}/items/completednew (unified "completed" rule)

Note: the /families/{familyId}/ prefix comes from the initial front contract but no longer fits the model (sharing is per user, not family-scoped). To reconfirm with the front: either keep it as a mere display context, or switch to /magic-lists/{id}. Out of brainstorm scope.

Domain-cross-cutting work:

  • Serialize createdAt / updatedAt in the views (list, summary, items).
  • camelCase convention on all input/output DTOs (#[serde(rename_all = "camelCase")]).
  • Item mutations return the full MagicList (front alignment).
  • Wire the cross-cutting sharing: check_magic_list_access delegates to the cross-cutting access resolution; add the sharing block (visibility/sharedWith/access) to the views.
  • Apply rights (write 6 ⇒ items; owner ⇒ list admin — see Access & sharing section).

Phase 2 — Templates

  • Generation endpoint: POST /families/{familyId}/magic-lists/{templateId}/generate (payload: name, target type SIMPLE|TASK). The generated instance is personal; sharing is then done via the (cross-cutting) sharing endpoint.
  • Generate the list from the template: load the template + its items, create a new independent list, copy the items resetting checked/status.
  • No FK constraint template→instance.
  • Add the front UI (the mock and the front do not have it yet → the contract is to be created, not aligned).

Decisions journal (revisable)

  • D1 — 3 types kept; checked and status coexist on TASK; checkbox shown for TASK only.
  • D2 — Item content optional (title alone mandatory). Corrects the initial spec.
  • D3 — Shared list: write (6) = collaborative on items, admin (rename/sharing/deletion) reserved to the owner. (Now expressed via the cross-cutting bitmask — see sharing.html.)
  • D4 — Templates handled in Phase 2 (after CRUD parity).
  • D5 — excludedMemberIds applied in access control. Obsolete: excludedMemberIds/familyId/visibility no longer exist on magic_list; sharing is per user via the cross-cutting mechanism (sharing.html). Exclude = do not create a grant.
  • "Completed" rule = checked || status == DONE (unifies clearing + grouping).
  • Filters/search/sort on the front in phase 1.
