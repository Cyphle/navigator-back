#4 bank accounts (front real / back read-only)

Context

Track family and personal money: an account holds a starting balance and four kinds of movement — recurring charges (out), one-off credits (in), one-off expenses (out), and budgets (spending envelopes with their own expenses). The user wants a per-month view with a real balance and a pessimistic end-of-month forecast.

State of the code: the front is real (list, month detail, overviews, summary, and create operations). The back has the domain entities but is read-only stub (summary/overviews return []; computed amounts hardcoded to 0). The front contract is the reference; deltas decided here are listed in their own section.

Ownership & sharing

An account is user-owned (decision B1). The front fields visibility (SHARED/PERSONAL) and familyId are removed, and the back Visibility enum is dropped from this domain. Access beyond the owner is delegated to the cross-cutting sharing mechanism (see sharing.html): owner has full rights; other users see/edit only through a matching share grant. Invisible account → 404; visible without write right → 403. The families/{familyId} path segment is a front grouping; the back resolves access via owner/share.

Data model

Only the database model is treated as technical here. Recurring amounts (charges, budgets) are versioned over time (decisions B3, B4): the amount is not a single column but a history of effective-dated versions.

    pub id: i32,
    pub name: String,
    pub owner_username: String,
    pub starting_amount: BigDecimal,
    pub start_date: NaiveDate,
    pub created_at: DateTime,
    pub updated_at: DateTime,
    // collections: budgets, charges, credits, expenses
}

    pub id: i32,
    pub account_id: i32,
    pub description: String,

    pub stop_date: Option<NaiveDate>,    // set on delete (B8)

pub struct Budget {                  // spending envelope
    pub id: i32,
    pub account_id: i32,
    pub name: String,
    pub periodicity: BudgetPeriodicity,  // MONTHLY | YEARLY | ONE_SHOT

    pub stop_date: Option<NaiveDate>,    // set on delete (B8)

    pub expenses: Vec<BudgetExpense>,
}

pub struct AmountVersion {           // versioned amount of a charge / budget
    pub id: i32,
    pub amount: BigDecimal,
    pub effective_from: NaiveDate,   // applies from this period onward (B3)
}

pub struct Credit {                  // one-off inflow (B5)
    pub id: i32,
    pub account_id: i32,
    pub description: String,
    pub amount: BigDecimal,
    pub credit_date: NaiveDate,
}

pub struct Expense {                 // one-off outflow, outside any budget
    pub id: i32,
    pub account_id: i32,
    pub description: String,
    pub amount: BigDecimal,

}

pub struct BudgetExpense {           // outflow inside a budget envelope
    pub id: i32,
    pub budget_id: i32,
    pub description: String,
    pub amount: BigDecimal,
    pub expense_date: NaiveDate,
    pub debit_date: NaiveDate,
}

pub enum ChargePeriodicity { Monthly, Yearly }
pub enum BudgetPeriodicity { Monthly, Yearly, OneShot }

Tables: bank_accounts, charges, charge_amounts (versions), budgets, budget_amounts (versions), budget_expenses, credits, expenses. Sharing reuses the cross-cutting shares table — no family/visibility column anywhere.

JSON convention: camelCase (startingAmount, startDate, creditDate, debitDate, effectiveFrom, createdAt, updatedAt). Enums in SCREAMING_SNAKE (MONTHLY, YEARLY, ONE_SHOT). Mutations return the full BankAccount aggregate.

The two dates

Every outflow carries two dates (decision B7):

DateMeaningDrives
expenseDatewhen the expense was madewhich month it belongs to / which budget month it consumes
debitDatewhen it shows on the accountthe actual vs forecast split (debitDate ≤ today = already debited)

Example: expenseDate=31/03, debitDate=02/04 → the expense belongs to March, but counts toward the real balance only once 02/04 is reached.

Budgets, charges and amount versioning

A budget is a spending envelope; a charge is a recurring outflow. Both are recurring and aligned to calendar periods (decision B3):

  • MONTHLY: spans a whole calendar month, even if created mid-month (never 08/03→08/04).
  • YEARLY: spans the civil year, even if created mid-year.
  • ONE_SHOT (budget only): a single finite envelope.

Amount versioning (B3, B4): changing the amount applies to the period of the change and all following periods, never the past. The amount applicable to a period P is the latest version with effectiveFrom ≤ P.

Example: restaurant budget 1000 from 01/01/2026; changed to 2000 on 25/06 → 2000 for June–December 2026; changed again in July → applies July onward. June stays at the value it had.

A recurring charge/budget is stored once with bounds [startDate, stopDate?]; the back projects one occurrence per period within the requested window. Charges are recurring only — a one-off outflow is an Expense, not a charge.

Computed amounts

For a requested month M (decisions B2, B7):

FieldDefinition
currentAmount (budget)applicable amount of the budget for M − sum of its budget expenses assigned to M (by expenseDate). The envelope's remaining money.
actualAmountreal balance: startingAmount + Σ(credits − charges − expenses − budget expenses) whose debitDate ≤ today.
remainingAmount / endOfMonthForecastpessimistic end-of-M balance: take everything assigned to ≤ M (debited or not) and reserve the full envelope of each active budget (instead of its actual expenses). Worst case. The two names are synonyms across views.
totalCredits / totalExpensesmonth M sums (by creditDate / expenseDate).
monthLabeldisplay label, e.g. "Mars 2026".

A month's opening balance is recomputed from the full transaction history (approach already noted in the back code — acceptable for a household-sized account).

Managing an account (CRUD)

Full CRUD on the account and its sub-entities (decision B6). Every mutation returns the full BankAccount aggregate.

  • Account: create (name, startingAmount, startDate), rename, delete (cascade on sub-entities + sharing grants).
  • Charge / budget — amount: editing the amount creates a version with effectiveFrom = current period (applies to that period and following).
  • Charge / budget — name/description: plain non-versioned update.
  • Charge / budget — delete: sets stopDate (stops the recurrence; past months keep it — decision B8).
  • Credit / expense / budget expense: create, edit, plain delete (one-off, no versioning).

Views & endpoints

Endpoints kept from the front contract under families/{familyId}/bank-accounts:

  • GET /summary → dashboard items: { id, name, actualAmount, endOfMonthForecast }.
  • GET /overviews?month=YYYY-MM → per-account overview for the month (startingAmount, actualAmount, remainingAmount, totalCredits, totalExpenses, budgets with remainingAmount).
  • GET /{id}?year=&month= → month detail (monthLabel, remainingAmount, actualAmount, budgets as month views, charges, credits, expenses).
  • Create operations: account, budget, budget expense, charge, credit, expense (plus the update/delete added by B6).

Errors & HTTP codes

Project common principle, standard web codes: 404 absent/invisible account or sub-entity, 403 visible without the required right, 400 invalid input (amount ≤ 0, bad dates, stopDate < startDate, effectiveFrom before the entity start).

Listed edge cases

  • expenseDate ≠ debitDate across a month boundary → month by expenseDate, actual/forecast by debitDate (B7).
  • Amount changed mid-period → applies to that period onward; previous periods keep their version (B3, B4).
  • Deleting a recurring charge/budget → stop from a date; past months unaffected (B8).
  • Budget expense exceeding the envelope → allowed; currentAmount goes negative (forecast already reserves the full envelope).
  • Future-month view → nothing debited yet, so actualAmount = opening balance; remainingAmount = projection.
  • One-off outflow → an Expense, never a charge.

Decisions journal (revisable)

  • B1 — Account is user-owned; sharing cross-cutting. visibility/familyId removed; Visibility enum dropped from this domain.
  • B2 — actualAmount = starting + transactions debited (debitDate ≤ today); remainingAmount/endOfMonthForecast = worst-case end of month (undebited included + budgets reserved at 100%).
  • B3 — Budget periodicity MONTHLY (calendar month) / YEARLY (civil year) / ONE_SHOT; amount versioned (change applies to its period and following, never past).
  • B4 — Charges use the same versioned-amount logic.
  • B5 — Credits are one-off only (salary is never identical month to month, so not recurring).
  • B6 — Full CRUD on account + sub-entities.
  • B7 — Month assignment by expenseDate; debitDate drives the actual/forecast split.
  • B8 — Deleting a recurring charge/budget stops it from a date; the past is kept.
  • Charge = recurring only (MONTHLY/YEARLY); a one-off outflow is an Expense.
  • endOfMonthForecast = remainingAmount — same computation, two names depending on the view.
